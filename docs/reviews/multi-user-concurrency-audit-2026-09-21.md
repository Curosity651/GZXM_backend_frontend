# 多用户并发与数据一致性审查（2026-09-21）

## 结论

本次覆盖系统管理、课题、科研指标、单位指标分配、成果、月季报、归档和文件上传的主要写入流程。课题、指标、成果和月季报已有较完整的行锁、版本号或幂等键保护。本次发现并修复 3 类可复现的数据竞争：同一文件票据并发写入、系统账号并发更新、归档自定义文件夹重名并发创建。

## 已修复

### CON-01 同一文件票据并发上传或完成

- 风险：两个请求可同时向同一对象键写入，完成接口也可能重复通过 `PENDING` 校验。
- 修复：`FileObjectMapper.lockById` 使用 `SELECT ... FOR UPDATE`；上传及完成都在事务内锁定文件记录。NAS 写入采用临时对象加 `MOVE`，失败时不留下正式半文件。
- 结果：相同票据严格串行，后到请求会读取到最新状态。

### CON-02 用户状态、密码、资料和角色并发修改

- 风险：多个管理员同时修改同一用户时，旧实体可能覆盖新的 `token_version` 或资料字段，导致已签发令牌未按预期失效。
- 修复：用户写操作先锁定 `sys_user`；角色权限更新先锁定 `sys_role`。权限替换与相关用户令牌失效仍在同一事务中完成。
- 结果：同一用户或角色的写操作串行执行，不再丢失计数型更新。

### CON-03 归档文件夹并发重名

- 风险：“先查询、再插入”在两个并发请求下可能同时通过，生成两个同名有效文件夹；模板初始化也有同类问题。
- 修复：新增仅约束未删除文件夹的数据库生成列和唯一索引；自定义创建捕获唯一键冲突并返回 `ARCHIVE_FOLDER_EXISTS`；模板初始化改用幂等插入。
- 结果：数据库作为最终一致性防线，同一归档范围内只允许一个有效同名文件夹。

## 已确认具备保护的流程

- 课题编辑：课题行锁 + `recordVersion` 条件更新。
- 科研指标草稿/发布：课题行锁 + `draftVersion` + 发布快照唯一键。
- 单位指标分配：课题行锁 + `draftVersion` + 指标发布版本校验 + 发布快照唯一键。
- 成果编辑和三轮审批：成果行锁 + `recordVersion`/`submittedVersion` + 幂等操作记录。
- 月季报编辑和审批：报告行锁 + `recordVersion`/`submittedVersion` + API 幂等键；创建周期由唯一键兜底。
- 配套自筹项目编辑：`recordVersion` 条件更新，受影响行数二次确认。
- 归档文件关联：文件夹行锁 + `(folder_id,file_id)` 唯一键；移除为条件更新。

## 保留的设计取舍与后续建议

- 角色权限和指标草稿采用“整份方案替换”语义。并发请求会被串行化或因版本过期被拒绝，但业务上最后一次成功提交仍代表完整方案，这是当前界面契约。
- 工作台和统计接口由多条只读查询组成；并发提交发生在查询期间时，极短时间内不同卡片可能来自相邻提交时点。这不会写坏数据。如需财务级同一时点报表，可后续把统计聚合改为单条 SQL 或使用只读一致性快照。
- NAS 与数据库无法组成分布式事务。当前采用临时对象、状态机、完成校验和孤儿清理实现最终一致性；这是 WebDAV 场景下比长时间持有跨系统事务更可控的方案。
