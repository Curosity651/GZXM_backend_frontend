## 5. 缺陷清单

### FST-01 [P1] 工作台“指标目标”统计口径错误

- 位置：`frontend/src/pages/HomePage.tsx:55-67`。
- 现状：只读取排序最后一个时间阶段的 `indicator-targets`，并将基础指标和专项指标全部相加。
- 正确口径：按选定节点累计所有阶段的基础指标；专项指标是基础成果的子集，不应重复加入总目标。
- 隔离数据实测：页面算法得到 23，成果进度后端按正确累计基础口径得到 25。
- 影响：工作台完成率、缺口和目标数均可能错误。

### FST-02 [P1] 工作台遗漏“正式终审已通过”的论文和专利

- 位置：`frontend/src/pages/HomePage.tsx:65,96`。
- 现状：页面要求 `status === 'EFFECTIVE' && countsToIndicator` 才计为完成。
- 业务规则：论文录用、专利授权在第二轮双审通过后即完成，此时状态可能是 `WAIT_PUBLICATION` 或 `WAIT_GRANT`，但 `countsToIndicator=true`。
- 隔离数据实测：同一条 `WAIT_PUBLICATION + countsToIndicator=true` 记录，工作台算法得到 0，后端成果进度得到 1。
- 影响：生效成果数、课题完成数和完成率被低估。

### FST-03 [P1] 工作台将草稿课题计入课题数量和执行概览

- 位置：`backend/src/main/java/com/gzxm/server/modules/dashboard/api/DashboardController.java:32`、`frontend/src/pages/HomePage.tsx:49,54`。
- 现状：仅按 `enabled=true` 筛选，没有排除 `status=DRAFT`。
- 隔离数据实测：1 个已实施课题加 1 个草稿课题后，工作台返回课题数 2，而成果进度业务范围只有 1 个课题。
- 影响：违反“草稿课题不能被成果、进度、归档业务检索”的既定规则，工作台统计范围与业务页不一致。

### FST-04 [P1] 后端自动化基线因需求变更未同步，无法可靠拦截回归

- 40 项课题测试仍使用没有内部/外部课题单位账号绑定的普通单位，全部在创建课题时返回 `TOPIC_UNIT_ROLE_REQUIRED`。
- 9 项成果测试仍断言旧草稿可见范围或旧错误码。
- 1 项成果统计测试仍按旧“节点值即累计值”口径断言，当前系统已经改为“阶段值求累计”。
- 影响：全量测试持续失败时，新引入的真实缺陷容易被噪声掩盖。

### FST-05 [P2] 停用课题在配置页可读，但从成果进度汇总中消失

- 位置：`backend/src/main/java/com/gzxm/server/modules/topic/application/DefaultTopicQueryService.java:24-31`。
- 现状：`listReadableTopics` 直接排除 `enabled=false` 的课题；显式详情读取仍允许全局角色查看。
- 自动化证据：`pausedTopicAndDisabledNodeStayReadableAndDraftTargetsDoNotOverridePublished` 找不到停用课题统计行。
- 需确认：若“停用即软删除并隐藏”则应更新测试和产品说明；若“停用只读但仍可查看历史”则应修复汇总范围。

### FST-06 [P2] 工作台待办和成果数存在固定分页截断

- 位置：`frontend/src/pages/HomePage.tsx:49-52`、`frontend/src/api/achievement-api.ts`。
- 现状：报告列表未传分页，默认只取 20 条；成果与课题最多取 200 条后在前端聚合。
- 影响：数据超过阈值后，“当前待审批”“生效成果”和课题执行概览不完整。后端已经返回 `pendingReports`，但前端没有使用。

### FST-07 [P2] 工作台存在未使用的归档请求，归档故障会拖垮整个工作台

- 位置：`frontend/src/pages/HomePage.tsx:47-53`。
- 现状：`Promise.all` 调用了 `archiveApi.directories()`，但解构结果没有使用；该请求失败仍会使整个工作台进入失败状态。
- 影响：增加无效请求和加载时间，并扩大单个模块故障的影响范围。

### FST-08 [P2] 成果统计只信任 `counts_to_indicator`，缺少非法状态防御

- 位置：`backend/src/main/java/com/gzxm/server/modules/achievement/application/DefaultAchievementProgressQuery.java:106`。
- 现状：只要标志为真，即使数据库记录处于 `DRAFT` 也会计入有效成果；数据库也没有限制状态与标志的组合。
- 自动化证据：人为构造 `DRAFT + counts_to_indicator=true` 后，期望 1、实际统计 2。
- 影响：正常 API 不会生成该组合，但数据迁移、人工修数或异常回滚可能污染统计。

## 6. 契约与工程问题

1. 静态 OpenAPI 有 76 个操作，运行时有 77 个；运行时 `GET /reports/{reportId}/reviews` 没写入静态契约。
2. 6 个 operationId 在静态契约与运行时不一致：当前用户、刷新令牌、修改用户、修改密码、修改角色权限、报告审批记录。这会影响代码生成和契约回归。
3. 项目要求的 `openapi-spec-validator==0.7.2` 在当前 Python 包源不可用，包源最高仅提供 0.5.7，完整 OpenAPI 3.1 校验未能执行；本次完成了路径与 operationId 的结构比对。
4. 报告、归档和工作台缺少控制器级集成测试。本次通过隔离环境人工自动化脚本验证了主流程，但这些流程尚不能由仓库内测试稳定复现。
5. 前端生产包体积 1.36 MB，后续可按页面懒加载拆包；当前不影响功能正确性。

## 8. 修复顺序建议

1. 先修复 FST-01、FST-02、FST-03，使工作台与成果进度的统一统计口径一致。
2. 同步修复后端测试夹具和旧断言，让 170 项测试恢复全绿。
3. 明确停用课题是“隐藏”还是“历史只读可见”，再处理 FST-05。
4. 将工作台统计改为专用后端聚合接口，避免前端分页聚合、状态口径分叉和多模块请求耦合。
5. 补齐报告、归档、工作台的集成测试，并修复 OpenAPI 契约漂移。
